# CLAUDE.md 管理插件 - 快速参考指南

## 一句话总结

**通过"代码驱动审计（带量化评分 + 报告先行）" + "会话驱动捕获"两个互补闭环 + 严格价值过滤 + 人类审批门控，持续保持 CLAUDE.md 成为高密度、当前可信的项目记忆源，解决 AI 编码智能体长期使用中的上下文腐烂问题。**

---

## 核心原则速查表

| 原则 | 核心表述 | 实践要点 |
|------|----------|----------|
| 报告先行，写入有门 | 永远先输出完整质量报告 + 具体 diff + 收益理由，用户批准后才 Edit | 杜绝静默/无审计的记忆变更 |
| 只记高价值增量 | 只添加"未来会话会感谢"的非显而易见、项目特定、可复现、可行动信息 | 每行必须赚回它占用的 token |
| 双循环缺一不可 | 审计循环保"与代码库同步"，捕获循环保"会话洞察不流失" | 重大变更后 audit；任意会话结束前 revise |
| 分层清晰，隔离污染 | 项目级（git 共享） vs 本地级（.claude.local.md + gitignore） vs 全局 vs 包级 | 个人偏好绝不进团队 CLAUDE.md |
| 模板是起点，验证是必须 | 用模板初始化，但必须用真实命令、路径、结构、quirks 填充并交叉验证 | 拒绝占位符和未定制内容 |
| 极简优于完备 | Dense、表格、一行描述、可复制命令 > 长篇解释 | 让 CLAUDE.md 成为人类和 agent 都爱读的文件 |

## 质量评分 6 维度检查清单（满分 100）

使用 improver 时或手动评估时逐项打分：

1. **Commands/Workflows (20分)**
   - 构建、测试、开发、lint、部署等核心命令是否都有？
   - 是否带必要上下文（端口、环境、注意事项）？
   - 常见操作是否一目了然？

2. **Architecture Clarity (20分)**
   - 关键目录及其职责是否解释清楚？
   - 模块/包关系、数据流是否描述？
   - 入口点、配置位置是否明确？

3. **Non-Obvious Patterns (15分)**
   - 真正会踩坑的 gotchas、workarounds 是否记录？
   - "为什么我们这么做" 的设计缘由是否在？
   - 边缘案例、顺序依赖是否提及？

4. **Conciseness (15分)**
   - 是否有明显可从代码推断的废话？
   - 是否存在冗余或跨文件重复？
   - 每条信息是否真正"加分"？

5. **Currency (15分)**
   - 记录的命令现在还能跑吗？
   - 引用的文件/目录还存在吗？
   - 技术栈描述是否与实际一致？

6. **Actionability (15分)**
   - 命令可以直接复制粘贴执行吗？
   - 步骤具体、路径真实吗？
   - 新人/新会话能否据此快速上手？

**快速分级参考**：90+ A（典范）、70+ B（良好）、50+ C（及格但有明显缺口）、<50 必须优先修复。

**红旗清单**（发现立即标记）：
- 命令会失败（路径错、缺依赖）
- 引用已删除的文件/文件夹
- 明显从模板复制未替换的项目名/命令
- 大段"TODO"从未完成
- 通用建议（"写测试""用有意义变量名"）

## 内容取舍决策树（TO ADD vs NOT TO ADD）

**问自己这 5 个问题，全部为"是"才考虑加入：**

1. 这个信息**从代码/目录结构本身看不出来**吗？（非 obvious）
2. 它是**本项目特有**的，而不是放之四海而皆准的最佳实践吗？
3. 它**会反复出现**（而非一次性 bug 修复）吗？
4. 它**可被未来会话直接行动**（命令可复制、路径真实、步骤具体）吗？
5. 它**值得占用提示词 token**，能让未来 Claude 少走弯路或少问问题吗？

**坚决不加（常见陷阱）**：
- 类/函数/文件的一句话描述（名字已经说明）
- "Always write tests"、"Use meaningful names" 等通用教条
- "我们在 commit abc123 修了登录按钮"（不会复现）
- JWT 是什么、REST 是什么的长篇科普
- 模板里的空章节或示例占位符

**优先加入（高杠杆）**：
- 实际可执行且之前缺失的核心命令 + 简要说明
- 必须按特定顺序执行或必须用特定 flag 的操作
- 共享状态导致的测试隔离要求
- 构建时 vs 运行时变量的区别
- 关键包/模块的初始化顺序依赖
- 真实遇到过的、会让新手/新会话浪费时间的 quirks

## 常见问题快速修复

| 症状 | 根本原因 | 立即修复动作 |
|------|----------|-------------|
| Claude 反复问"怎么 build / test / 启动" | Commands 缺失或已过时 | 运行 improver 审计，补充真实命令表格，验证可执行后写入 |
| Agent 在正确目录下仍做错事 | Architecture / Key Files 缺失或过时 | 补充简洁的目录树 + 关键文件列表 + 用途；交叉验证 |
| 总是踩同一个已知坑 | Gotchas / Non-Obvious Patterns 完全空白 | 收集最近 3-5 个真实踩坑案例，用 1 行描述 + 规避方法写入 |
| CLAUDE.md 越来越长但越来越没用 | 没有执行价值过滤，收录了大量 obvious/generic | 用 update-guidelines 的 NOT TO ADD 清单做一次大扫除，只保留高价值条目 |
| 个人本地设置污染团队文件 | 混用了 CLAUDE.md 而非 .claude.local.md | 立即迁移个人内容到 .claude.local.md 并 gitignore；团队文件只留共享 |
| 多个 CLAUDE.md 内容重复或矛盾 | 缺少分层治理和同步机制 | 明确根 vs 包级职责；根只放跨包内容，包级放专属内容 |
| 改了代码但 CLAUDE.md 没更新 | 缺少触发习惯 | 把"重大变更后必须 audit / revise"写入团队工作流与 CONTRIBUTING |

## 与本项目其他方法论的结合点

**本插件是"记忆基础设施"，其他方法论是"流程与能力封装"，结合后效果 1+1>2：**

- **Vibe Coding 不是工程**：工程前置 9 大领域决策（invariants、identity、constraints...）产出的 INVARIANTS.md / BOUNDARIES.md 等，正是 improver 应该重点审计和保护的核心高价值内容。使用本插件可确保这些工程决策产物不腐烂。
- **Superpowers**：设计门控阶段产生的规格文档、审查发现的问题，可在 verify 后通过 revise-claude-md 精炼为 CLAUDE.md gotchas 条目。两阶段审查中的"规格合规审查"可参考 improver 的质量报告。
- **GSD 工作流**：plan-phase 产出的结构化计划、verify 阶段的验证发现、discuss 阶段识别的灰色领域，都是极佳的 revise 原材料。GSD 的原子提交习惯也便于回溯"这次改动该不该进 CLAUDE.md"。
- **Claude Skills 构建指南**：技能的 SKILL.md、references/ 本身也需要良好的 CLAUDE.md 支撑。 improver 可用于确保整个 .claude/skills/ 目录的上下文文件质量。技能的"渐进式披露"理念与 CLAUDE.md 的"只保留高价值"原则高度一致。
- **上下文工程 / Agentic File System**：CLAUDE.md 是最高优先级、常驻加载的上下文层之一。本插件提供的质量 gate + 过滤器是让"文件系统持久化上下文"真正可信、可持续的维护机制。
- **Browser-Use / AutoHarness 等执行类**：在复杂操作 agent 中，"操作不变量""合法动作集""环境 quirks"正是 Non-Obvious Patterns 部分应重点记录的内容。

**快速决策**：
- 想让 agent 少重复发现 → 优先用 /revise-claude-md 形成捕获习惯
- 想系统性对齐当前代码库 → 定期运行 improver 审计 + 报告驱动修复
- 想把其他方法论的洞察固化 → 在对应工作流末尾增加"输出可写入 CLAUDE.md 的精炼条目"步骤

## 快速实施模板

### 1. 结束会话时的 revise 最小流程（复制用）

```
/revise-claude-md
```
或按 `#` 键。

然后按其 5 步走：Reflect → Locate → Draft（保持一行一个概念） → Show diff+why → 获批后 Apply。

### 2. 推荐的 CLAUDE.md 根项目最小骨架（用后填充真实内容）

```markdown
# <Project Name>

<一行描述>

## Commands

| Command | Description |
|---------|-------------|
| `...` | ... |

## Architecture

```
<真实目录树 + 简要职责>
```

## Key Files

- `...` - ...

## Gotchas

- <真实踩坑 + 规避，项目特有>
```

### 3. 提议更新的标准 diff + why 格式（improver 内部使用，也可手动）

```markdown
### Update: ./CLAUDE.md

**Why:** 之前缺失生产构建命令，导致 agent 多次猜测并执行错误命令。

\`\`\`diff
 ## Commands

+| Command | Description |
+|---------|-------------|
+| `npm run build:prod` | 完整生产构建（带优化、类型检查、资源指纹） |
\`\`\`
```

### 4. 首次审计后的行动清单（推荐复制到个人 notes）

- [ ] 运行 improver，获得基线质量报告
- [ ] 优先处理评分 <70 的文件
- [ ] 对每条推荐，用"5 问过滤器"决定是否采纳
- [ ] 批准后应用，提交 CLAUDE.md 变更（附报告片段）
- [ ] 建立结束会话习惯（/revise-claude-md 或 #）
- [ ] 把 .claude.local.md 加入 .gitignore（如使用）
- [ ] 1 周后复审一次，观察分数是否提升、会话摩擦是否下降

## 实际案例效果预期（基于方法论设计）

- **短期（首次审计后）**：快速补齐缺失命令与 gotchas，agent 第一次回答准确率显著提升。
- **中期（习惯固化 2-4 周）**：CLAUDE.md 平均质量分数从 C/B 提升到 A/B，"Claude 又问我..." 类问题大幅减少。
- **长期**：项目记忆成为可信资产，新成员/新会话 onboarding 时间缩短；与 Superpowers/GSD/Claude Skills 叠加后，形成"工程纪律 + 流程门控 + 记忆卫生"的完整防护体系。
