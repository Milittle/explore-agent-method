# Vibe Coding Is Not Engineering - 快速参考指南

## 一句话总结

**Vibe Coding 产出 demo 代码；Engineering 在代码生成之前定义系统的不变量、身份规则、约束边界和失败模式，使代码能在真实运行时系统中长期安全运行。** LLM/agent 是极强的代码生成器，但不是工程师——人类必须始终保持对 intent、constraints、trade-offs 的判断中心地位。

---

## 核心原则速查表

| 原则 | 核心表述 | 实践要点 |
|------|----------|----------|
| 工程先于代码 | 所有关键决策必须在任何代码（包括 AI 生成）存在之前完成 | 永远不要直接扔需求给 AI 先要工程决策 |
| 系统 ≠ 代码文本 | 系统是代码 + 运行环境 + 操作规则 + 不变量 + 因果结构的整体 | 关注“变更后整个系统会怎样”，而不是“这段代码能不能跑” |
| LLM 的真实能力边界 | LLM 擅长 Additive pattern extension，不擅长 Transformative causal reasoning | 新功能 vs 修改核心 = 不同策略 |
| 人类判断必须中心化 | AI 放大工程产能，但不移除工程判断 | 门控、审查、最终决策权保留给人类 |
| Demo 是可丢弃的，产品不是 | 能跑的原型距离可维护生产系统还有巨大工程鸿沟 | 原型之后必须走完整工程流程 |

## 工程前置决策 9 大领域检查清单（最重要）

每次使用 AI 生成/修改代码前，逐项确认：

1. **Invariants（不变量）** — 什么必须永远为真？（列出 3-5 条）
2. **Identity & Uniqueness（同一性与唯一性）** — 什么让一个实体成为“它自己”？关键字段是否必须唯一？如何判定“同一个用户/订单”？
3. **Constraints（约束）** — 系统绝对不允许发生什么？（业务规则、合法状态、顺序）
4. **Failure Modes（失败模式）** — 前 3 个最可能的压力/错误场景？系统该如何检测、降级、恢复？
5. **Coupling & Sequencing（耦合与顺序）** — 哪些操作必须严格顺序？哪些可以并行？依赖关系图是什么？
6. **State & Transitions（状态与转换）** — 状态机是什么？允许的转换有哪些？非法转换如何阻止？
7. **Interfaces & Contracts（接口与契约）** — 各部分对外部承诺什么行为保证？输入输出 Schema + 不变量？
8. **Boundaries（边界）** — 这个系统/模块明确不负责什么？防止蔓延的防火墙在哪里？
9. **Error Handling & Recovery（错误处理与恢复）** — 异常时如何保持系统处于可预测状态？补偿/回滚/告警策略？

**最小版本（紧急时至少回答前 4 条）** 也可大幅降低风险。

## 常见问题快速修复

| 症状 | 根本原因（按本文） | 立即修复动作 |
|------|-------------------|-------------|
| AI 生成的代码反复在生产出“不可能”的状态 | 缺失 invariants / constraints 定义 | 立即补充 INVARIANTS.md，加入 agent 必读上下文 + 写对应测试门控 |
| 多个用户/实体身份混乱 | 缺少 identity & uniqueness 决策 | 显式定义“什么构成同一个实体”，加唯一索引 + 应用层守卫 |
| 简单改动引发连锁故障 | 没有分析 coupling / downstream 后果 | 强制做“变更影响分析”（至少列出受影响的不变量和模块） |
| 新功能加得很快，但整体越来越难改 | 边界隐式膨胀，缺少 Architecture Decision | 补充 BOUNDARIES.md，设立显式“模块职责防火墙” |
| Agent 在遗留系统上表现远不如新项目 | 任务是 Transformative 而非 Additive | 切换策略：重度人工前置 + 系统模型上下文 + 更严格审查 |
| 团队对 AI 输出既爱又怕 | 缺少工程门控，导致“看起来能跑”与“实际安全”是两回事 | 建立不可跳过的 Engineering Gate + 制品检查 |

## 与本项目其他方法论的结合点（决策树）

**想用本文洞察加强现有流程？**

- **Superpowers 框架**：直接把“9 大领域检查清单”注入到“设计门控”阶段的规格文档模板中；利用“两阶段审查”中的第一阶段（规格合规）强制验证工程决策完整性。
- **GSD 工作流**：在 discuss-phase 重点做 problem framing + 关键不变量；在 plan-phase 产出结构化的工程决策（可作为 PLAN.md 的前置 section）；verify 阶段增加对 invariants 的自动化+人工双重检查。
- **上下文工程（Context Engineering）**：把本文的工程决策（invariants、boundaries、key decisions）作为最高优先级、常驻加载的上下文层（PROJECT/INVARIANTS 级别），通过文件系统持久化解决 LLM “看不到完整系统”的问题。
- **Claude Skills**：将“工程前置 9 大领域 + 快速检查清单”封装为常驻 skill（description 包含“任何 coding 任务必须先完成工程决策”触发语），实现 100% 强制触发。
- **Anthropic Cookbook 工作流模式**：Evaluator-Optimizer 模式非常适合“工程决策验证”——先由一个 agent 提出决策，再由 evaluator agent 按本文表格打分/挑刺；Orchestrator-Workers 可用于复杂系统的多维度工程建模（状态、接口、失败）。
- **Browser-Use 等执行类 agent**：在浏览器自动化等“行动密集”场景中，同样需要前置定义“操作不变量”（如“永远不要在未验证状态下提交表单”）和失败恢复策略。

**快速选择**：
- 纯新增、边界清晰的小功能 → 可偏向 agent 加速 + 轻量工程前置（至少回答 1-4 条）。
- 修改核心、跨模块、涉及状态的 → 必须重度工程前置 + 人类最终确认 + 影响分析。
- 长期维护 / 生产关键系统 → 工程决策制品必须作为仓库一级资产，与代码并重。

## 实际案例效果（来自文章 + 实践推断）

- **反面**：简单“添加用户登录”vibe code → 缺少邮箱唯一性 → 生产中出现重复账号、密码重置核弹、删除波及多用户等不可接受后果。
- **正面**（结合 Superpowers/GSD 实践）：在设计门控或 plan 阶段强制填写上述模板后，AI 生成的代码会自然遵守已声明的不变量和边界；后期返工率和生产 incident 显著降低；团队对“AI 辅助”的信任度从“试试看”变成“可依赖的加速器”。
- **量化感受**（社区常见反馈）：前置工程决策通常只增加 15-30% 局部时间，却能避免 80%+ 因“隐式假设被打破”导致的后续灾难性返工。

## 关键行动（今天就能做）

1. **今天**：复制“工程前置 9 大领域检查清单”，贴在你最常用的 AI coding 工具旁。
2. **下个任务**：在扔需求给 agent 之前，先花 10 分钟填“快速实施模板”前 4-5 项。
3. **本周**：在你当前的主要 agent 工作流中，硬性增加一个不可跳过的 Engineering Gate。
4. **本月**：为当前项目补一个 INVARIANTS.md（至少 5-8 条核心不变量），并配置为 agent 高优先级只读上下文。
5. **持续**：每完成一个用 AI 辅助的特性，用本文表格做一次 5 分钟复盘，记录“这次被跳过的工程决策”。

**记住**：  
AI 让写代码变得极快，但“让系统保持安全和连贯”这件事，仍然是工程判断的工作。  
代码是廉价的，判断不是。
